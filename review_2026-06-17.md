## CPU backend (cross-backend reference)

### `cpu-math`  (0C / 0H / 1M / 3L)

#### [MEDIUM][correctness] where_batch SIMD selects wrong branch for NaN condition (diverges from its own scalar tail and PyTorch)
- **Location:** src/backends/cpu/kernels/simd_fast_math.hpp:850 (where_batch_avx2), 880 (where_batch_avx512)
- **Problem:** Both where_batch functions compute the truth mask with `_mm256_cmp_ps(c, zero, _CMP_NEQ_OQ)` / `_mm512_cmp_ps_mask(c, zero, _CMP_NEQ_OQ)`. `_CMP_NEQ_OQ` is the *ordered* not-equal predicate: when an operand is NaN it returns FALSE, so a NaN condition lane is treated as 'false' and `blendv` selects `y`. But the scalar tail in the SAME function (line 857: `(cond[i] != 0.0f) ? x[i] : y[i]`) and the scalar fallback in the only caller (src/backends/cpu/kernels/indexing.cpp:1057 `is_cond_true` and 1073-1074) evaluate `NaN != 0.0f` which is TRUE in C++, selecting `x`. So a floating `where` condition containing NaN yields different output for SIMD-enabled vs scalar builds, and the SIMD vector body even contradicts its own scalar remainder for the same array. PyTorch treats any nonzero (NaN included) condition as true, matching the scalar path; the SIMD path is wrong.
- **Fix:** Use the *unordered* predicate so NaN compares not-equal-to-zero (true) like C++: replace `_CMP_NEQ_OQ` with `_CMP_NEQ_UQ` in both where_batch_avx2 and where_batch_avx512. This makes NaN lanes select `x`, matching the scalar tail, the non-SIMD fallback, and PyTorch.

#### [LOW][correctness] f32_to_bf16_scalar uses an off-by-one round-to-nearest-even bias (diverges from AVX2/AVX512 BF16 converters)
- **Location:** src/backends/cpu/kernels/bfloat16_simd.hpp:53
- **Problem:** The scalar F32->BF16 converter sets `rounding_bias = (bits & 0x00010000u) ? 0x00007FFFu : 0x00007FFEu`, i.e. bias = 0x7FFE + lsb16. The canonical round-to-nearest-even bias (and what the SIMD siblings cvt_f32_to_bf16_avx2 at line 81 and cvt_f32_to_bf16_avx512 at line 130 use) is `0x7FFF + lsb16`. At an exact tie (low 16 bits == 0x8000) with lsb16==1, correct RNE must round UP to make the result even: bias 0x8000 produces a carry (0x8000+0x8000=0x10000). The scalar version uses bias 0x7FFF (0x8000+0x7FFF=0xFFFF, no carry) and therefore rounds DOWN, leaving an ODD low bit — the opposite of round-to-even. This silently produces a 1-ULP-different BF16 than the SIMD path for tie cases. The function currently has no callers (only bf16_to_f32_scalar is used, at math.cpp:1067-1068), so it is latent, but it is an exported helper that any future code may use, and it disagrees with the live SIMD converters.
- **Fix:** Match the SIMD path / canonical formula: `uint32_t lsb = (bits >> 16) & 1u; uint32_t rounding_bias = 0x00007FFFu + lsb;` (equivalently change the literals to 0x8000u : 0x7FFFu). Then `bits += rounding_bias; return bits >> 16;`.

#### [LOW][design] Dead vectorized sin/cos/pow/leaky_relu in simd_fast_math.hpp risk divergent edits; misleading about the live CPU path
- **Location:** src/backends/cpu/kernels/simd_fast_math.hpp:278-401 (pow_avx2/sin_avx2/cos_avx2/leaky_relu_avx2) and 554-651 (AVX512 variants)
- **Problem:** sin_kernel/cos_kernel (math.cpp:4482-4599) and pow_kernel (math.cpp:3413-) deliberately use libm `std::sin/std::cos/std::pow` (the inline comments at math.cpp:4500-4502 and 3423-3425 say the SIMD polynomial paths were abandoned because they lost significance / clamped negative bases). A tree-wide grep shows sin_avx2/cos_avx2/pow_avx2/leaky_relu_avx2 (and their AVX512 forms) are referenced ONLY from within simd_fast_math.hpp itself (cos calls sin, the scalar-exponent pow overload calls the vector pow) — no CPU op-path caller. They are effectively dead code. Beyond being unused, the cos->sin large-argument fallback compares |x_orig| where x_orig is already x+pi/2, so the dead path also has a latent edge bug. Keeping these alongside the live libm kernels invites a future maintainer to 'fix' or wire up the wrong implementation and reintroduce the precision regression the comments describe.
- **Fix:** Delete the unused sin_avx2/cos_avx2/pow_avx2(/scalar)/leaky_relu_avx2 and their AVX512 counterparts (as was already done for the tanh-GELU helpers per the NOTE at lines 403-407), or guard them behind an explicit opt-in and add a comment that the live trig/pow CPU kernels use libm. At minimum, document at the top of the file that these vector transcendentals are NOT the path used by sin/cos/pow ops.

#### [LOW][correctness] SIMD log_avx2/log_avx512 return finite garbage for +inf and mishandle subnormals (exposed dispatch entries)
- **Location:** src/backends/cpu/kernels/simd_fast_math.hpp:152-218 (log_avx2), 463-510 (log_avx512)
- **Problem:** The vectorized log extracts exponent/mantissa via integer bit-twiddling and only special-cases x<0 (NaN) and x==0 (-inf). For x = +inf (exp field 0xFF, mantissa 0) it computes e = 128, m = 1.0, u = 0, giving a finite result ~88.7 instead of +inf. For subnormal inputs (exp field 0, mantissa != 0) it treats the value as 2^-127 * (1.something) by OR-ing in the implicit 0x3f800000 leading bit, producing a result that does not match std::log of the subnormal. These functions back g_dispatch.log (simd_dispatch.cpp:379/405) and the exp/sigmoid/tanh siblings have the analogous inf-clamp at simd_fast_math.hpp:105-107. The math.cpp log_kernel/exp_kernel use libm so the main op path is unaffected, which is why this is LOW, but g_dispatch.log/exp are public dispatch entries that any future kernel could call and would then silently diverge from CPU/PyTorch on inf/subnormal inputs.
- **Fix:** Add explicit handling in log_avx2/log_avx512: blend +inf where x==+inf (e.g. mask `_CMP_EQ_OQ` against `+inf`), and either flush subnormals or route subnormal/inf lanes to a scalar std::log fallback (mirroring the big-argument scalar fallback already used in sin_avx2). Alternatively document that g_dispatch.log is approximate and must not be used where inf/subnormal correctness matters.

### `cpu-reduction`  (0C / 0H / 2M / 2L)

#### [MEDIUM][correctness] argmax/argmin do not propagate NaN, diverging from max/min and PyTorch
- **Location:** src/backends/cpu/kernels/reduction.cpp:2017-2140 (argmax_impl, argmax_along_dim), 2381-2453 (argmin_impl, argmin_along_dim), and the Float16/BFloat16 argmax/argmin branches 2179-2266, 2491-2665
- **Problem:** Every argmax/argmin path reduces with bare `input_data[i] > max_val` / `< min_val` comparisons. These are false for any NaN operand, so NaN inputs are silently skipped and the returned index is that of a non-NaN element. PyTorch/NumPy semantics: if any element along the reduced dimension is NaN, argmax/argmin returns the index of (the first) NaN. The sibling `max_kernel`/`min_kernel` in this same file deliberately propagate NaN (max_along_dim line 1500-1514 sets `saw_nan` and returns quiet_NaN), so `max(x)` reports NaN while `argmax(x)` reports a finite index pointing at a different element — internally inconsistent and divergent from the CPU reference contract the rest of the file follows.
- **Fix:** Mirror the max_along_dim NaN logic in argmax (and min logic in argmin): while scanning, if `std::isnan(static_cast<double>(input_data[in_idx]))` (or the Float32-widened value for half types), record that index and stop, returning it as the argmax/argmin result. Apply to argmax_impl, argmax_along_dim, argmin_impl, argmin_along_dim, and all four Float16/BFloat16 inline loops so full-reduction and dim paths agree.

#### [MEDIUM][correctness] logsumexp dim-reduction casts double max to float for isinf, falsely shortcuts large finite Float64 inputs
- **Location:** src/backends/cpu/kernels/reduction.cpp:4091
- **Problem:** In logsumexp_along_dim, after computing the per-slice max `m` (type Acc, which is `double` for the Float64 dispatch at line 4233), the inf check is `if (std::isinf(static_cast<float>(m)))`. Casting a large but finite double (e.g. m = 1e300) to float overflows to +inf, so std::isinf returns true and the code writes `output_data[out_idx] = T(m)` (line 4092) — taking the 'max is infinite' shortcut and skipping the exp-sum entirely. The result is m alone instead of the correct `m + log(sum(exp(x-m)))`, wrong for any Float64 slice whose maximum magnitude exceeds ~3.4e38. The full-reduction path (logsumexp_full_impl line 4035) correctly uses `std::isinf(m)` on the native Acc type, so the dim path diverges from the full-reduction path and from PyTorch.
- **Fix:** Use `std::isinf(m)` directly (Acc-typed, no float cast), matching logsumexp_full_impl line 4035. The float cast was presumably added for Float16/BFloat16 where Acc=float anyway; for those Acc is already float so the direct call is equivalent, and for double it fixes the spurious overflow.

#### [LOW][correctness] histogramdd auto-detected upper range can drop the maximum sample (boundary recompute mismatch)
- **Location:** src/backends/cpu/kernels/reduction.cpp:4607-4609 vs 4639
- **Problem:** Edges are built as `edata[i] = fmin + i*step` so the true upper edge is `edata[nb]`. The in-range test at line 4639 instead recomputes the upper bound as `fmin_d + step_d * static_cast<T>(nb)`. With floating-point rounding these two expressions are not guaranteed bit-identical to `fmax` (and `fmin + nb*step != fmax` in general because step itself was rounded). When ranges are auto-detected, fmax equals the data maximum, and a sample exactly equal to the maximum can test `v > fmin_d + step_d*nb` as true and be dropped from the histogram (the 1-D histogram_kernel at line 4518 avoids this by comparing against the stored tmax directly). This silently loses counts versus NumPy/torch.histogramdd, which include the right-closed maximum.
- **Fix:** Compare against the actual computed upper edge `edata[nb]` (or the stored `ranges[d].second`) rather than recomputing `fmin_d + step_d*nb`, and make the last-bin clamp (line 4645) the mechanism that keeps the maximum sample, consistent with the 1-D histogram_kernel.

#### [LOW][performance] argmin full-reduction is single-threaded while argmax is parallelized (perf asymmetry)
- **Location:** src/backends/cpu/kernels/reduction.cpp:2381-2395 (argmin_impl) vs 2017-2082 (argmax_impl)
- **Problem:** argmax_impl has a full OpenMP per-thread-partial parallel implementation for n >= REDUCTION_OMP_THRESHOLD (lines 2033-2081). argmin_impl is a plain serial loop with no OpenMP path at all, so full-reduction argmin over large tensors runs single-threaded and is markedly slower than the otherwise-symmetric argmax. This is a maintainability/perf inconsistency between two sibling ops that should behave identically.
- **Fix:** Give argmin_impl the same padded per-thread LocalMin + sequential merge structure as argmax_impl (with `<` comparisons and lowest-index tie-break), so large-tensor argmin matches argmax throughput.

### `cpu-activations`  (0C / 0H / 4M / 0L)

#### [MEDIUM][correctness] sigmoid_backward_kernel reads inputs with flat indexing but never calls .contiguous() (wrong gradient on non-contiguous grad/input)
- **Location:** src/backends/cpu/kernels/activations.cpp:572-660
- **Problem:** sigmoid_backward_kernel takes `grad_output` and `input` directly and iterates them with flat pointer indexing (`grad_out_data[i]`, `in_data[i]`) after `grad_input = zeros_like(input)`. zeros_like always returns a fresh CONTIGUOUS tensor (src/ops/creation.cpp:986-989 -> zeros()), so grad_input is written densely while grad_output/input are read densely. If either grad_output or input is a non-contiguous view (e.g. a transposed or broadcast-expanded gradient, which routinely occurs in autograd), the flat read picks up the wrong logical elements and the gradient is silently wrong. Every FORWARD kernel in this same file (sigmoid_kernel l.449, tanh_kernel l.669, relu_kernel l.287, etc.) defensively calls input_raw.contiguous() with an explicit comment 'flat-pointer iteration requires contiguous input' (audit-2026-05-03 bug #15), and sibling BACKWARD kernels relu_backward (l.314-315), gelu_backward (l.934-935), swish_backward (l.1069-1070), elu_backward (l.2191-2192), selu_backward (l.2315-2316), mish_backward (l.2470-2471) all call .contiguous() on both args. These four backward kernels deviate from that established convention.
- **Fix:** At the top of sigmoid_backward_kernel, mirror the siblings: `auto grad_output = grad_output_raw.contiguous(); auto input = input_raw.contiguous();` (rename the parameters to *_raw) before taking data<T>() pointers.

#### [MEDIUM][correctness] tanh_backward_kernel never calls .contiguous() on grad_output/input
- **Location:** src/backends/cpu/kernels/activations.cpp:802-858
- **Problem:** Same defect as sigmoid_backward: tanh_backward_kernel(grad_output, input) iterates both with flat indexing (`grad_out_data[i]`, `in_data[i]`) and writes into a contiguous `zeros_like(input)`, but never materialises contiguous copies of the inputs. A transposed/broadcast (non-contiguous) grad_output or input yields a wrong gradient, while sibling backward kernels (relu/gelu/swish/elu/selu/mish) and all forward kernels in this file guard with .contiguous(). Registered and dispatched via OpId::TanhBackward (cpu_kernel_registry.cpp:1442).
- **Fix:** Add `auto grad_output = grad_output_raw.contiguous(); auto input = input_raw.contiguous();` at the function start (renaming params to *_raw), matching tanh_kernel and the other backward kernels.

#### [MEDIUM][correctness] leaky_relu_backward_kernel never calls .contiguous() on grad_output/input
- **Location:** src/backends/cpu/kernels/activations.cpp:1226-1319
- **Problem:** leaky_relu_backward_kernel(grad_output, input, alpha) reads both tensors with flat pointer indexing (including the AVX-512/AVX2 _mm*_loadu paths for Float64) and writes into a contiguous `zeros_like(input)`. It never materialises contiguous copies, so a non-contiguous grad_output/input (common for gradients flowing through transposed views) produces a silently wrong gradient. The forward leaky_relu_kernel (l.1138) and sibling backward kernels do call .contiguous(); this one is inconsistent. Registered via OpId::LeakyReluBackward (cpu_kernel_registry.cpp:1466).
- **Fix:** Add `auto grad_output = grad_output_raw.contiguous(); auto input = input_raw.contiguous();` at the top (renaming the parameters), consistent with the forward kernel and the other backward kernels.

#### [MEDIUM][correctness] softplus_backward_kernel never calls .contiguous() (and writes empty() output without it)
- **Location:** src/backends/cpu/kernels/activations.cpp:2659-2746
- **Problem:** softplus_backward_kernel(grad_output, input, beta, threshold) allocates `grad_input = empty(shape, ...)` (contiguous) and fills it with flat indexing while reading grad_output/input with the same flat indexing, but never calls .contiguous() on the inputs. A non-contiguous grad_output or input therefore yields a wrong gradient. Note this is worse than the others because it uses empty() rather than zeros_like(), so any divergence is not even zero-initialised. The forward softplus_kernel (l.2578) explicitly calls input_raw.contiguous() with the standard comment, but the backward does not. Registered via OpId::SoftplusBackward (cpu_kernel_registry.cpp:1488).
- **Fix:** Materialise contiguous copies of both inputs at the top: `auto gout = grad_output.contiguous(); auto in = input.contiguous();` and use those for the data<T>() pointers (and for the shape used to allocate grad_input).

### `cpu-nn-norm`  (0C / 0H / 1M / 2L)

#### [MEDIUM][correctness] BatchNorm Float16/BFloat16 mean/variance computed-in-float but stored as half, then normalize/forward recompute invstd entirely in half precision — large divergence from CPU float reference
- **Location:** src/backends/cpu/kernels/batchnorm.cpp:247-258 and 416
- **Problem:** batchnorm_mean_var_impl<Float16>/<BFloat16> correctly accumulate the mean and variance in float (Kahan), but then narrow and store them as half (mean[c]=Float16(channel_mean) line 247; variance[c]=Float16(sum_sq_diff/total) line 258). The forward normalize path batchnorm_forward_impl<T> (line 416) then reads these half stats and computes `invstd = T(1.0f)/safe_sqrt(channel_var+epsilon)` ENTIRELY in half precision (T=Float16). Float16 has ~10 mantissa bits and max ~65504, so (a) any per-channel variance > 65504 saturates to +inf -> invstd=0 -> all-zero output, and (b) the reciprocal-sqrt loses precision the float-accumulated variance was meant to preserve. This diverges from the CPU Float32 reference (which keeps everything in float) and from the backward path, which explicitly uses an Acc=float accumulator type (bn_acc<Float16>::type=float, lines 934-936) and computes invstd in float (line 979). Forward and backward therefore use different precision for the same quantity.
- **Fix:** Make the half forward/normalize path mirror the backward's bn_acc<T> approach: in batchnorm_forward_impl and batchnorm_forward_affine_impl, compute invstd/scale/bias for Float16/BFloat16 in float (cast var/mean/gamma/beta to float, compute invstd=1.0f/sqrtf(var+eps) and scale/bias in float, then narrow only the final per-element output). Alternatively store batch mean/variance as Float32 buffers for half inputs (as LayerNorm does for its saved stats) so the stats never round-trip through Float16.

#### [LOW][correctness] Embedding forward applies padding_idx after negative-index normalization but compares against the raw (un-normalized) padding_idx, so a negative padding_idx is silently never honored while embedding_backward ignores padding_idx entirely
- **Location:** src/backends/cpu/kernels/nn_kernels.cpp:896 and 924-996
- **Problem:** In embedding_kernel the lookup index is negative-normalized (line 895: if(idx<0) idx+=num_embeddings) and then compared to the raw parameter via `if (padding_idx >= 0 && idx == padding_idx)` (line 896). PyTorch's nn.Embedding accepts a negative padding_idx (e.g. -1 = last row) and zeros that row's output AND zeros its gradient. Here the `padding_idx >= 0` guard means a negative padding_idx is silently ignored in the forward, and embedding_backward_kernel (lines 924-996) never receives or applies padding_idx at all, so even a valid non-negative padding_idx row accumulates a nonzero gradient — diverging from PyTorch which keeps weight[padding_idx] frozen. The default padding_idx=-1 (no-padding sentinel) makes the forward guard correct, but a user-supplied negative padding_idx is mishandled.
- **Fix:** Normalize padding_idx the same way as idx before comparison (int64_t pad = padding_idx; if(pad<0 && pad!=-sentinel) pad+=num_embeddings) and use an explicit 'has padding' flag rather than overloading -1. Thread padding_idx into embedding_backward_kernel and skip/zero the grad accumulation for the padding row to match PyTorch's frozen-padding-row semantics.

#### [LOW][performance] BatchNorm AVX-512 mean/var fold-in of the scalar remainder loses the parallel-Welford precision advantage by re-running a serial Welford on top of an already-merged accumulator
- **Location:** src/backends/cpu/kernels/batchnorm.cpp:128-139 and batchnorm_avx512.cpp:101-112
- **Problem:** Both SIMD mean/var kernels read each channel's data twice: once in the vectorized Welford loop and again in the scalar remainder fold-in loop (line 130-139 in batchnorm.cpp; 103-112 in batchnorm_avx512.cpp), which re-walks all N batches for the (spatial_size % WIDTH) tail elements. For NCHW tensors whose H*W is not a multiple of 8/16 this doubles the per-channel memory traffic for the tail and re-streams the whole channel pointer set a second time. The tail elements could instead be folded inside the single n-loop right after the SIMD inner loop (using the already-loaded ch_ptr), avoiding the second pass over the input.
- **Fix:** Move the scalar remainder accumulation into the same `for n` loop as the SIMD inner loop (immediately after the `for(; i+W<=spatial_size; ...)` block, continue the same i to spatial_size folding into a per-lane-0 scalar Welford state), then merge that scalar state once during the horizontal lane merge. This keeps a single pass over the input.

### `cpu-conv-pool`  (0C / 0H / 1M / 2L)

#### [MEDIUM][design] Duplicate Winograd F(2,3) implementation: inline copy in conv2d_forward_impl diverges from winograd.hpp and is the sole path for Float64 3x3 stride-1 convs
- **Location:** src/backends/cpu/kernels/conv2d.cpp:874-1044 (vs src/backends/cpu/kernels/winograd.hpp:58-208)
- **Problem:** There are two independent, hand-written Winograd F(2x2,3x3) transforms. winograd.hpp::winograd_conv2d_f2x3 (the float-only path the kernel dispatcher actually calls at conv2d.cpp:1224-1229) and a second full re-implementation embedded inside the dtype-generic template conv2d_forward_impl<T> (conv2d.cpp:874-1044). Because conv2d_forward_kernel routes Float32 isotropic 3x3 stride-1 groups-1 convs through winograd.hpp before ever reaching conv2d_forward_impl, the inline copy is dead for Float32 but is the ONLY Winograd path exercised for Float64 (conv2d_forward_impl<double> at line 1255 falls into the line-874 block). The two copies carry the same transform matrices today, but any future fix to one (e.g. a precision tweak or a boundary fix for odd output sizes) will silently NOT apply to the other, and the Float64 path has no test coverage that the Float32 path's dispatch reaches. This is exactly the 'dead/duplicate kernel definitions that risk divergent edits' class.
- **Fix:** Make winograd.hpp::winograd_conv2d_f2x3 a template on the accumulator/element type (or add a double overload) and call it from both the Float32 dispatcher and conv2d_forward_impl<double>, deleting the inline copy at conv2d.cpp:874-1044. Alternatively, drop the inline Winograd block entirely and let Float64 3x3 take the im2col+GEMM path (correct, just slower) so there is a single Winograd source of truth.

#### [LOW][design] Comment claims MKL is required for the Float64 conv GEMM path, but the generic template silently provides a (scalar) Float64 GEMM when MKL is absent
- **Location:** src/backends/cpu/kernels/conv2d.cpp:19-25 and 234-256; src/backends/cpu/kernels/conv3d.cpp:15-19
- **Problem:** The header comments (conv2d.cpp:19-22, conv3d.cpp:15-16) state the Float64 path needs MKL cblas_dgemm 'otherwise the Float64 conv resolves to the generic scalar triple loop'. That is accurate, but the gemm_cpu<double> / gemm_local<double> MKL specializations are wrapped in #ifdef TENZOR_USE_MKL (conv2d.cpp:322-344, conv3d.cpp:177-195). When MKL is not compiled in, gemm_cpu<double> resolves to the primary template gemm_cpu<T> (conv2d.cpp:234) whose accumulator is `T sum = T(0)` i.e. genuine double — so results stay correct but ~10x slower with no diagnostic. The risk is purely that a non-MKL Release build silently loses the documented BLAS path for every Float64 convolution; there is no runtime signal that the fast path was dropped.
- **Fix:** No correctness change needed. Either add a one-time TENZOR_LOG_WARN when the non-MKL Float64 conv path is taken on large problems, or update the comment to make explicit that the fallback is correct-but-slow so reviewers don't mistake the scalar path for a precision regression.

#### [LOW][correctness] im2col/im3col offset and index arithmetic can overflow int64 for very large feature maps with no guard, unlike calculate_output_size
- **Location:** src/backends/cpu/kernels/conv3d.cpp:53-54 (im3col_cpu total) and conv2d.cpp:94-101
- **Problem:** im3col_cpu computes `int64_t total = batch * out_d * out_h * out_w * col_cols` (conv3d.cpp:54) and im2col indexes `((b*channels+c)*height+ih)*width+iw` (conv2d.cpp:108) using int64 products with no overflow guard, whereas the output-size helper calculate_output_size (conv2d.cpp:61-64) does guard dilation*(kernel-1). For pathological but legal 5D shapes (e.g. batch*out_d*out_h*out_w*(C*kD*kH*kW) exceeding 2^63) the flat-index loop bound silently wraps negative and the loop body is skipped, leaving the col buffer (and thus the conv output) partially uninitialized rather than throwing. This is an edge case (requires ~9e18 elements) but the asymmetry with the guarded helper makes it a latent silent-wrong-result path.
- **Fix:** Guard the col-buffer element count the same way calculate_output_size guards: check that batch*out_*...*col_cols does not overflow int64 (or simply that each multiplicative step stays below INT64_MAX) before allocating/looping, and throw std::invalid_argument otherwise. The 2D im2col path (conv2d.cpp) should get the same guard for consistency.

### `cpu-fused-rnn`  (0C / 0H / 2M / 1L)

#### [MEDIUM][correctness] oneDNN GRU uses vanilla gru_forward (linear_before_reset=0) but Tenzor's GRU reference is linear_before_reset=1
- **Location:** src/backends/cpu/kernels/rnn_onednn.hpp:896 (gru_forward_onednn) and 1381 (gru_multilayer_forward_onednn)
- **Problem:** All native CPU GRU references in scope (gru_forward_f64 at rnn_kernels.cpp:265, gru_cell_fused at fused_lstm.hpp:865, gru_cell_forward_kernel at rnn_kernels.cpp:580) implement PyTorch's linear_before_reset=1 new-gate math: n = tanh(W_in@x + b_in + r * (W_hn@h + b_hn)) — the hidden bias b_hn is added BEFORE the reset-gate multiply. The nn layer (src/nn/layers/gru.cpp:386-388) explicitly documents that Tenzor's GRU is linear_before_reset=1 and that mode-0 must fall through to the autograd path. However gru_forward_onednn and gru_multilayer_forward_onednn build the primitive with dnnl::gru_forward, which is oneDNN's VANILLA GRU (linear_before_reset=0); oneDNN exposes a SEPARATE primitive dnnl::lbr_gru_forward for the lbr=1 contract. When a nonzero hidden-side bias reaches these primitives the result diverges from the CPU reference because b_hn lands post-reset instead of pre-reset. This is currently latent because the single-layer gru_forward_kernel only routes to oneDNN when there is no bias at all (rnn_kernels.cpp:1217) and the GRUMultiLayerForward fast path was disabled in the nn layer (gru.cpp:407), but the GRUMultiLayerForward op is still registered to gru_multilayer_forward_kernel (cpu_kernel_registry.cpp:2588) and forwards a per-layer bias into gru_forward_onednn / the fused primitive, so a direct dispatch<OpId::GRUMultiLayerForward> with bias produces GRU output inconsistent with the reference.

#### [MEDIUM][correctness] SliceScatter resolves negative `end` with an off-by-one (`+ dim_size + 1`), diverging from PyTorch/Slice semantics

#### [MEDIUM][correctness] clamp on NaN diverges: CUDA collapses NaN to min_val, CPU preserves NaN
- **Location:** src/backends/cuda/kernels/math.cu:868-881 (clamp_kernel_f32/f64)
- **Problem:** clamp_kernel_f32 computes `fminf(fmaxf(val, min_val), max_val)` (line 871; f64 uses fmin/fmax at 879). CUDA's fmaxf/fminf return the non-NaN operand when one input is NaN, so a NaN input becomes `fminf(min_val, max_val) = min_val` — NaN is silently replaced by the clamp lower bound. - **Fix:** Preserve NaN in the CUDA float/double clamp kernels, e.g. `float v = input[idx]; output[idx] = ::isnan(v) ? v : fminf(fmaxf(v, min_val), max_val);` (and the double analogue). This matches the CPU reference and PyTorch semantics.

#### [MEDIUM][correctness] Complex division uses naive denominator and overflows where CPU (std::complex / Smith) does not
- **Location:** src/backends/cuda/kernels/math.cu:1108-1118 (complex_div_kernel) and 1144-1153 (ComplexDivOp)
- **Problem:** Both compute `denom = br*br + bi*bi` then divide (lines 1114-1116, 1149-1151). For large-magnitude divisors this squares into overflow: e.g. Complex64 with br~1e20 gives denom = 1e40 > FLT_MAX (~3.4e38) → +Inf, so a finite result like (1e20)/(1e20) returns 0 instead of 1; near-underflow inputs similarly lose precision. The CPU reference divides via `std::complex<T>::operator/` (src/backends/cpu/kernels/math.cpp:1963-1965, 1989-1991 use std::complex), which on libstdc++ uses Smith's scaled algorithm and avoids this overflow. Cross-backend divergence on complex divide with large/small magnitudes.
- **Fix:** Use Smith's algorithm in the CUDA complex div kernels: if `fabs(br) >= fabs(bi)`, let `r = bi/br`, `d = br + bi*r`, real = `(ar + ai*r)/d`, imag = `(ai - ar*r)/d`; else swap roles. Apply to both complex_div_kernel and ComplexDivOp to match std::complex semantics.

#### [LOW][correctness] randint range scaling done in float32 biases/loses precision for large ranges
- **Location:** src/backends/cuda/kernels/math.cu:4116-4128 (randint_kernel_device)
- **Problem:** `int64_t val = low + static_cast<int64_t>(r * static_cast<float>(range));` (lines 4123-4124) casts the int64 range to float32 and multiplies a float32 uniform sample. For ranges above 2^24 (~16.7M) the float cannot represent consecutive integers, so the mapping skips integer values and the output distribution is biased / cannot cover all values — a correctness defect for Int64 randint over wide ranges. curand_uniform's limited mantissa compounds this.

#### [HIGH][correctness] Vulkan max-pool-with-indices stores GLOBAL flat index; CPU/CUDA store per-channel spatial index (h*W+w)  — ✅confirmed
- **Location:** src/backends/vulkan/kernels/pooling_forward_with_indices.comp:56-63,74 (and _f16:84, _f64:60 variants)

The Int32 indices tensor is returned unchanged to the caller (src/backends/vulkan/vulkan_ops_pooling.cpp:40,125), so on Vulkan a user gets indices that differ from every other backend (off by `n*C*H*W + c*H*W`). #### [HIGH][security] Vulkan max_unpool2d will write out of bounds when fed Vulkan max-pool's global indices (no bounds check)  — ✅confirmed
- **Location:** src/backends/vulkan/kernels/max_unpool2d.comp:22-26
- **Problem:** max_unpool2d.comp treats the stored index as a PER-CHANNEL SPATIAL offset: `uint base_out = channel_idx * params.out_spatial; int unpool_idx = indices_data[idx]; output_data[base_out + uint(unpool_idx)] = input_data[idx];`. - **Fix:** Fix the maxpool index convention (companion finding) so unpool receives per-channel spatial indices, AND add a guard: `if (unpool_idx >= 0 && uint(unpool_idx) < params.out_spatial) output_data[base_out + uint(unpool_idx)] = input_data[idx];` mirroring the bounds check already present in max_pool2d_backward_indices.comp:30.

- **Location:** src/onnx/exporter.cpp:1694-1761 (export_lstm) and 1834-1905 (export_gru)
- **Problem:** For bidirectional RNNs, num_directions=2 and the ONNX W/R/B initializer tensors are allocated as [num_directions, 4*H, input_size] / [num_directions, 4*H, H] / [num_directions, 8*H] (LSTM; GRU uses 3*H/6*H). However the memcpy that fills them copies only one direction's worth of data: e.g. w_3d at line 1749-1751 is sized [2, 4*H, input_size] but only 4*hidden_size*input_size*sizeof(float) bytes (one direction) are copied; r_3d (1757-1759) and bias_combined (1777-1784) do the same. The Tensor(shape,dtype,device) ctor zero-initializes (src/core/tensor.cpp:118-119, zero_init=true), so the second direction's half of each buffer is left as all-zeros. The exporter then sets direction='bidirectional' (lines 1809-1810 / 1940-1941). The result is a structurally valid ONNX bidirectional RNN whose reverse direction has zero weights/biases — the backward pass output is wrong (effectively only forward direction is meaningful). reorder_lstm_gates/reorder_gru_gates also only operate on the passed weight_ih/weight_hh, which carry a single direction's gate block, so there is no second-direction source being copied at all.
- **Fix:** Either (a) reject bidirectional RNN export with a clear 'not yet supported' error until reverse-direction weights are threaded through and packed into direction index 1, or (b) extend export_lstm/export_gru to accept the reverse-direction weight/bias tensors, reorder them, and memcpy them into the [1, ...] slice of W/R/B (offset 4*H*input_size etc.). At minimum, guard with a runtime check that num_directions*4*H*input_size floats are actually written before emitting the node.

#### [MEDIUM][correctness] LSTM/GRU gate reorder uses data<float>()/sizeof(float) and hardcoded DType::Float32, corrupting or rejecting non-Float32 RNN export
- **Location:** src/onnx/exporter.cpp:1700-1736 (reorder_lstm_gates), 1749/1757/1777, and the analogous GRU code 1839-1905
- **Problem:** reorder_lstm_gates allocates the output with cpu_w.dtype() (preserving the source dtype) but immediately accesses it through cpu_w.data<float>() / reordered.data<float>() and does all block copies in units of sizeof(float). The W/R/B 3D tensors at 1749, 1757, 1777 are hardcoded DType::Float32 and copied with sizeof(float) arithmetic. If an LSTM/GRU module holds Float64, Float16, or BFloat16 weights (a supported dtype per dtype_to_onnx at exporter.cpp:50-66), this either trips data<float>()'s dtype assertion or reinterprets the bytes at the wrong element width, silently corrupting the exported weights and exporting them mislabeled as FLOAT. There is no dtype guard before this path.
- **Fix:** Make reorder_lstm_gates dtype-generic (template on element size / dispatch on dtype, computing row_bytes from dtype_size(cpu_w.dtype())), and allocate w_3d/r_3d/bias_combined with the source dtype, copying numel*dtype_size bytes. Alternatively, assert weight_ih.dtype()==Float32 at entry and throw a clear 'only Float32 RNN export is supported' error so non-float32 weights fail loudly instead of being corrupted.

#### [LOW][design] ONNX export/import dtype mapping is asymmetric for UInt16/UInt32/UInt64: exporter emits them, importer rejects them
- **Location:** src/onnx/exporter.cpp:59-61 (dtype_to_onnx) vs src/onnx/importer.cpp:354-379 (onnx_to_dtype)
- **Problem:** dtype_to_onnx maps DType::UInt16/UInt32/UInt64 to ONNXDataType::UINT16/UINT32/UINT64, so a tensor of these dtypes can be exported to a valid ONNX file. onnx_to_dtype, however, has no case for UINT16/UINT32/UINT64 and falls into the default branch that throws 'Unsupported ONNX data type for import'. A model Tenzor itself exported with any of these unsigned dtypes therefore cannot be round-tripped back through this importer. This is an inconsistency between sibling export/import paths rather than a memory-safety issue.
- **Fix:** Either add UINT16/UINT32/UINT64 cases to onnx_to_dtype (mapping back to the corresponding DType), or remove/guard those cases in dtype_to_onnx so the asymmetry cannot arise (throwing at export time with a clear message instead of producing an unimportable file).
