KEY FEATURES IMPLEMENTED
================================================================================

✅ Memory Pooling and Reuse
   - Freed memory returns to cache instead of immediate device free
   - Best-fit allocation strategy using ordered set
   - Dramatically reduces cudaMalloc/cudaFree overhead

✅ Block Splitting
   - Large cached blocks split to satisfy smaller requests
   - Configurable minimum split size (default: 512 bytes)
   - Remaining fragments stay in cache

✅ Block Merging
   - Adjacent free blocks automatically merged
   - Reduces memory fragmentation
   - Configurable enable/disable
   - Forward merging implemented

✅ Thread Safety
   - Global mutex protection for all operations
   - Safe for concurrent access from multiple threads
   - Tested with parallel allocations

✅ Multi-Device Support
   - Per-device memory pools
   - Independent tracking for each CUDA device
   - Global aggregation for statistics

✅ Configurable Parameters
   - Memory alignment (default: 512 bytes, must be power of 2)
   - Maximum cached memory per device (0 = unlimited)
   - Block merging enable/disable
   - Minimum split size

✅ Comprehensive Statistics
   - Allocated, reserved, and cached bytes tracking
   - Operation counters (allocations, frees, cache hits)
   - Block manipulation stats (splits, merges)
   - Per-device and global views

✅ RAII Support
   - CachedMemoryGuard for automatic cleanup
   - Move semantics implemented
   - Exception-safe memory management

================================================================================
ARCHITECTURE HIGHLIGHTS
================================================================================

Design Pattern: Singleton with per-device pools
Allocation Strategy: Best-fit using std::set<Block*>
Thread Safety: std::mutex with lock guards
Memory Tracking: Three-tier statistics (allocated, reserved, cached)

Data Structures:
- std::set<Block*, BlockComparator>: Free blocks ordered by size
- std::unordered_map<void*, unique_ptr<Block>>: All blocks by pointer
- std::unordered_map<int, DeviceAllocator>: Per-device pools

Key Algorithms:
- Best-Fit Allocation: O(log N) using lower_bound
- Block Splitting: O(log N) insertion
- Forward Merging: O(log N) lookup and erase
- Cache Enforcement: O(K log N) where K = blocks to evict

USAGE INSTRUCTIONS
================================================================================

Enabling the Caching Allocator:
  export TENZOR_ENABLE_CACHING_ALLOCATOR=1

Basic Usage:
  auto& allocator = CachingAllocator::get();
  
  // Allocate
  void* ptr = allocator.allocate(1024 * 1024, device_id);
  
  // Use memory...
  
  // Free (returns to cache)
  allocator.free(ptr, device_id);
  
  // Check statistics
  auto stats = allocator.get_stats(device_id);
  std::cout << "Cache hit rate: " 
            << (100.0 * stats.num_cache_hits / stats.num_allocations) << "%\n";
  
  // Empty cache
  allocator.empty_cache(device_id);

RAII Pattern:
  {
      CachedMemoryGuard guard(4096, 0);
      void* ptr = guard.get();
      // Use memory...
  } // Automatically freed

Configuration:
  allocator.set_alignment(1024);           // 1KB alignment
  allocator.set_max_cached_memory(1GB);    // Limit cache size
  allocator.set_merge_enabled(true);       // Enable merging
  allocator.set_min_split_size(512);       // Min split size

================================================================================
DESIGN DECISIONS RATIONALE
================================================================================

1. Singleton Pattern
   Why: Centralized memory management, simpler API
   Trade-off: Global state, but necessary for memory pooling

2. Best-Fit Allocation
   Why: Balances speed (O(log N)) with fragmentation reduction
   Alternative considered: First-fit (faster) vs Worst-fit (less fragmentation)

3. Per-Device Pools
   Why: Prevents cross-device errors, scales to multi-GPU
   Benefit: Each device managed independently

4. Forward-Only Merging
   Why: Simpler implementation, still effective
   Future: Could add backward merging with address-sorted map

5. Environment Variable Toggle
   Why: Easy enable/disable without code changes
   Benefit: A/B testing, debugging, gradual rollout

6. CUDA Stubs
   Why: Allow compilation without CUDA toolkit
   Benefit: Tests can build on CPU-only systems

================================================================================
LIMITATIONS AND KNOWN ISSUES
================================================================================

Current Limitations:
1. Forward-only merging (backward merging not implemented)
2. Device ID lookup in free() uses cudaPointerGetAttributes (slight overhead)
3. No automatic cache eviction on OOM (manual empty_cache required)
4. Stream parameter stored but not used for allocation decisions

None of these limitations affect correctness or basic functionality.
