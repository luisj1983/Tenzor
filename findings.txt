[JIT-R023] MEDIUM (latent, no live trigger) — memory_planner.cpp's
compute_live_ranges/greedy_assign treat topological node-index as an
execution-time proxy; the invariant is unenforced and undocumented
File: src/jit/memory_planner.cpp:128-363 (esp. 298-305). Two live ranges are
considered safely non-overlapping purely by [begin,end] INDEX-interval
comparison — assumes node i's writes complete before node i+1 starts. Holds
for the current strictly-sequential interpreter but is nowhere enforced or
documented as a requirement.
NOTE: per the same review pass, this planner's output is not currently wired
to any real tensor-placement code anywhere in the codebase (see JIT-R024) —
so there is no live corruption risk today. This finding is about what
happens the moment that changes: if this plan is ever wired to a backend
that executes independent nodes concurrently (multi-stream CUDA/ROCm, or a
future IREE async lowering), two nodes with non-overlapping INDEX ranges but
overlapping REAL execution time could be aliased to the same buffer slot —
read of not-yet-written or already-overwritten data, only on whichever
backend's runtime schedules out-of-order/concurrently.
PARTIALLY ADDRESSED 2026-07-11: the underlying architectural gap (INDEX-
interval overlap isn't a valid proxy for execution-time overlap under
concurrent scheduling) genuinely can't be "fixed" without knowing the
requirements of a not-yet-built concurrent consumer — implementing that
now would be speculative, disproportionate new-feature work for code
nothing currently uses (JIT-R024). What WAS proportionate and done: added
an explicit doc comment directly on compute_live_ranges() stating the
invariant, why it currently holds (strictly-sequential interpreter), and
exactly when to re-verify it (before wiring this planner's output to any
backend that executes nodes concurrently) — closing the "unenforced AND
undocumented" half of the original finding; the enforcement-when-needed
half remains correctly deferred to whoever builds that consumer, same as
the still-open JIT-R024 dependency this finding already correctly noted.
Verified via test_memory_planner (7) and test_memory_planner_swap (3) —
zero regressions (doc-comment-only change).
Confidence: Medium (real gap, no live trigger — unchanged). Status: OPEN
(now documented; re-check/enforce when memory_planner output is wired to
actual concurrent execution).

[JIT-R106] CONFIRMED IREE/Vulkan-SPIR-V BUG (standalone repro landed
2026-07-11), NOT a Tenzor-side bug — Float16 SDPA NaN traced to a
convert(f16→f32)-into-dot_general fusion bug in IREE's Vulkan backend
File: test_jit_mlir_numeric_parity.cpp's
Float16ScaledDotProductAttentionParity (target=vulkan-spirv). Built a
standalone repro entirely outside Tenzor: dumped the real StableHLO Tenzor
generates for this exact case via CompiledFunction::dump_stablehlo(),
compiled it directly with `iree-compile --iree-hal-target-backends=
vulkan-spirv --iree-vulkan-target=ada` (this machine's real NVIDIA RTX 5070
Laptop GPU, a Blackwell-generation card — "ada" rather than "ampere" because
Tenzor's Vulkan IREE-target architecture detection was found and fixed this
session to route Blackwell/Ada NVIDIA GPUs to IREE's "ada" profile instead
of a stale hardcoded "ampere" that failed to even initialize on this
hardware; was tracked as JIT-R108, now fixed and removed from this file),
and ran it via
`iree-run-module` against the real Vulkan device, bisecting the dumped
module stage by stage:
  - Full SDPA pipeline standalone: reproduces the NaN exactly (matches
    Tenzor's failing test) — confirms this is not a Tenzor invocation
    artifact.
  - Softmax alone (reduce-max(-inf init)/subtract/exp/reduce-sum/divide, all
    F32): BIT-EXACT match vs llvm-cpu. Rules out the softmax pipeline
    entirely — the R106-original hypothesis (a stablehlo.reduce or divide/
    exponential SPIR-V bug) is WRONG.
  - QK dot_general + scale alone (transpose/reshape/convert-to-f32/
    dot_general/convert-back/reshape/multiply): reproduces massive
    divergence (values ~1e5-1e6 / inf vs correct O(1-10) values on CPU) —
    isolates the bug to before softmax, in the QK score computation.
  - Same dot_general with `precision = [HIGHEST, HIGHEST]` removed
    (DEFAULT precision): identical corruption — rules out the precision
    attribute as the trigger.
  - Same 32x32 matmul with NO batching dims (plain 2D dot_general,
    contracting_dims=[1]x[0] only): identical corruption — rules out
    batching as the trigger; this is a bug in basic F32 matmul codegen
    for this backend, unrelated to attention structure.
  - Same 32x32 matmul fed PURE F32 input (no f16 anywhere in the module):
    CORRECT (max abs diff ~1.9e-6, ordinary float noise) — the matmul
    codegen itself is fine.
  - `stablehlo.convert(f16→f32)` alone (reshape + convert, no matmul):
    BIT-EXACT (diff = 0.0) — the conversion codegen itself is fine.
  CONCLUSION: neither `stablehlo.convert(f16→f32)` nor `stablehlo.dot_general`
  is individually buggy on this IREE/Vulkan-SPIR-V backend + GPU/driver
  combination — the bug is specifically in the FUSION/INTERACTION when a
  convert's output feeds directly into a dot_general's operand (consistent
  with the "failed to legalize operation 'vector.bitcast'" warning seen when
  compiling this exact pattern against IREE's generic/no-target-resolved
  SPIR-V profile (encountered while isolating the now-fixed JIT-R108
  target-detection staleness) — suggesting the f16→f32 widening's
  vector-lane-packing lowering and the matmul's operand-loading codegen
  interact incorrectly, most likely a missing synchronization between the
  convert's compute dispatch and the matmul's, or an incorrect fused
  bitcast/lane-repacking assumption in the matmul's input-loading code).
Not a Tenzor-side bug: Tenzor's generated StableHLO is correct standard
MLIR; the same text lowers correctly on llvm-cpu/cuda/rocm. No Tenzor-side
workaround was attempted — the only credible mitigation (restructuring
Tenzor's lowering to prevent IREE from fusing the convert into the
dot_general, e.g. via an artificial op between them) would be a fragile,
unverifiable bet against IREE's current fusion heuristics rather than a
real fix, and risks silently breaking on a future IREE version; this is a
genuine upstream IREE bug that needs to be reported/fixed there.
Backends: Vulkan only (CPU/CUDA/ROCm all pass with the same MLIR
structure). Confidence: High (root cause isolated to a specific, minimal,
reproducible standalone construct — convert(f16→f32) feeding dot_general
— independent of Tenzor entirely). Status: OPEN — not fixable within
Tenzor; recommend filing an IREE upstream bug report with the minimal
repro modules saved this session as the reproduction case (the bisection
sequence above from full-pipeline down to the 2-op minimal repro), and/or
avoiding F16 SDPA on the Vulkan/IREE target until IREE fixes this (CPU/
CUDA/ROCm are unaffected and remain safe to use for this op+dtype+target
combination).
